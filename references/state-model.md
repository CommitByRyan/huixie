# 徽写 · 动态状态模型

## 为什么要独立一个 state.json

长篇吃书不是模型记性差，是**状态没有唯一出口**。当「主角现在受没受伤」「铜钥匙还在不在身上」「哪条线该兑了」散落在摘要、设定库、章节正文、作者记忆四个地方，每一章都要重新拼一次，拼错一次就吃书一次。

所以徽写把状态切成两层：

| 层 | 文件 | 变化频率 | 谁写 |
|---|---|---|---|
| 静态设定 | `novel.json`、`bible.json` | 基本不变 / 一季改一次 | 作者确认后手改 |
| 动态状态 | `state.json` | **每章都变** | `writeback.py` 增量写入 |

`state.json` 是写作时唯一可信的「此刻世界长什么样」。`ctx-NNN.md` 是它的一次投影，不是真相源。

## 伏笔四态

旧做法只有一个 `resolved: true/false`，结果「已放弃」「长期休眠」「作者拍板留白」全都堆在「未收」里，账越滚越大，最后每章都塞不下。

徽写用四个状态：

| status | 含义 | 能否被上下文选中 | 进入什么列表 |
|---|---|---|---|
| `open` | 活的，等兑现 | 能，按相关度排序 | 伏笔池 |
| `dormant` | 休眠，暂时不推 | 能，但降权 30 分 | 伏笔池（靠后） |
| `resolved` | 已兑现 | **不能** | 只进账，不再注入 |
| `abandoned` | 作者拍板不写 | **不能** | 只进账，留档 |

判定纪律：
- **推进 ≠ 兑现**。只是提到、只是加压、只是暗示，一律 `advance`，不进 `resolve`。
- `resolve` 必须带 `evidence`，而且 evidence 要能在正文里指认到一句话。
- `abandoned` 必须由作者明说，助手不能自己判放弃。

## 相关度算法

上下文装配时，伏笔按分数取前 N 条（默认 12）：

| 条件 | 加分 |
|---|---|
| 已到期（`due <= 当前章`） | +120 |
| 三章内到期 | +90 |
| 近 20 章内埋下 | +25 |
| 名字出现在本章要点里 | +60 |
| 名字的任一字出现在要点里 | +8 |
| `related_chapters` 含当前章 | +40 |
| `dormant` | −30 |
| `resolved` / `abandoned` | 直接排除 |

分数相同时，id 大的优先（近埋的线通常更该管）。

## 不变式（`lint` 会检查）

1. `state.chapter` 等于 `canon/` 里最大章号。
2. `threads` 的 `id` 不重复。
3. `status` 只能取四态之一。
4. `resolved` 的条目必须有 `resolved_at`。
5. 未收伏笔（open + dormant）超过 30 条时报警——这不是错误，但说明该收线了。
6. 同一章重复写回时，`_applied` 保证幂等；要覆盖必须显式 `--force`。

## 什么不该进 state.json

- 世界观、力量体系、人物出身 → 这些是静态，进 `novel.json` / `bible.json`。
- 整章剧情摘要 → 进 `chapters.json.summary` 与 `memory/`，state 只留「现在」。
- 大纲与未来剧情 → 进 `outline.json` / `seasons.json` / `beats/`。

state.json 越大，装配器越难把它压进预算。它应该像一张贴在墙上的便签，不像一本账。
